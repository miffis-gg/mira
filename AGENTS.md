# MIRA — инструкции для Codex

## 1. Назначение файла

Этот файл — главный источник инструкций для разработки демонстрационного лендинга салона красоты MIRA. Он связывает продуктовые, дизайнерские и структурные решения проекта.

Перед любыми изменениями необходимо полностью прочитать:

1. `AGENTS.md` — цели проекта, инженерные ограничения и критерии готовности.
2. `DESIGN.md` — визуальная система, сетка, типографика, изображения и адаптивность.
3. `STRUCTURE.md` — порядок секций, контент, данные и интерактивные сценарии.

При конфликте требований действует следующий приоритет:

1. прямое актуальное указание пользователя;
2. `AGENTS.md`;
3. `DESIGN.md` для визуальных решений;
4. `STRUCTURE.md` для контента и поведения;
5. существующие технические соглашения проекта.

Не переписывай документацию без необходимости. Если в спецификации есть небольшая неоднозначность, выбери наиболее практичное решение, соответствующее премиальному коммерческому сайту, и продолжай работу.

## 2. Суть проекта

MIRA — вымышленный премиальный салон красоты и «частный дом персонального образа». Проект создаётся как третий самостоятельный кейс для портфолио русскоязычного frontend-разработчика.

Задача сайта:

- сформировать ощущение высокого уровня сервиса без показной роскоши;
- помочь посетительнице выбрать направление и конкретную процедуру;
- показать прозрачные цены и продолжительность услуг;
- познакомить со специалистами и стандартами салона;
- сохранить выбранную услугу при просмотре страницы;
- довести посетительницу до понятной демонстрационной записи.

Основная аудитория — женщины примерно 23–50 лет, которым важны качество, спокойный сервис, эстетика, гигиена, понятная стоимость и возможность заранее спланировать визит.

Сайт должен восприниматься как реальный коммерческий лендинг, но все бренды, специалисты, цены, предложения, контакты и отзывы являются демонстрационными.

## 3. Позиционирование

MIRA не должна выглядеть как массовая сеть, свадебный салон, косметологическая клиника или шаблонный «женский» сайт.

Основная идея: премиальный сервис как персонально собранный визит. Посетительница не просто нажимает «записаться», а выбирает услугу, специалиста и подходящее время в спокойном сценарии «Ваш визит».

Тон бренда:

- уверенный;
- внимательный;
- деликатный;
- современный;
- лаконичный;
- без пафоса, уменьшительно-ласкательных слов и обещаний идеального результата.

Не использовать формулировки вроде «лучшая студия города», «безупречный результат», «эксперты №1», «гарантированное преображение» и другие неподтверждённые заявления.

## 4. Отличие от других проектов портфолио

Сайт обязан заметно отличаться от первых двух работ.

### Не повторять стоматологию «Белая линия»

- не использовать мятную медицинскую палитру;
- не строить интерфейс из множества мягких округлых карточек;
- не повторять композицию «проблема → рекомендация»;
- не использовать клиническую подачу и спокойную медицинскую пластику;
- не копировать структуру первого экрана, карточек специалистов и формы.

### Не повторять барбершоп «Лезвие»

- не делать угольно-чёрный брутальный сайт;
- не использовать узкую индустриальную типографику;
- не применять красно-оранжевый акцент;
- не повторять мужскую документальную стилистику;
- не копировать прямоугольную тяжёлую композицию и подачу прайс-листа.

### Собственная идентичность MIRA

- лаковый тёмно-сливовый как фирменное цветовое поле;
- фарфоровый и прохладный минеральный светлый фон;
- холодный металлический акцент вместо очевидного золота;
- редакционная, модная, но удобная композиция;
- сочетание выразительного display-шрифта и нейтрального кириллического гротеска;
- крупные фотографии с арт-дирекцией, а не набор одинаковых фотокарточек;
- асимметрия внутри строгой 12-колоночной сетки;
- сервисный сценарий «собрать визит» как ключевое взаимодействие.

## 5. Отсутствие AI-референса

Проект разрабатывается без AI-сгенерированного макета или изображения сайта-референса.

Запрещено:

- генерировать картинку готового сайта и затем копировать её;
- использовать AI-макет как пространственный контракт;
- подгонять HTML под случайные координаты из изображения;
- помещать текст интерфейса внутрь фотографии;
- копировать чужой сайт или отдельный премиальный бренд пиксель в пиксель.

Разработка ведётся code-first по правилам `DESIGN.md`. Визуальное качество достигается через сетку, типографику, реальные HTML-компоненты, фотонаправление, ритм секций и проверку отрендеренного результата.

Допускается использовать `imagegen` только для создания отдельных фотографических материалов, если это действительно необходимо. Такие изображения не должны содержать логотип, текст, цены, кнопки, элементы сайта или водяные знаки. Предпочтительны проверенные лицензированные фотостоки или самостоятельные фотографии с зафиксированным источником.

## 6. Использование Codex skills

Перед работой проверь доступные skills.

- Используй `impeccable` для проектирования, типографики, адаптивности, доступности, визуальной проверки и финальной полировки.
- Не запускай comp-first и не создавай AI-референс страницы: для этого проекта выбран code-first.
- Используй `imagegen` только для самостоятельных растровых фотографий или текстур, но не для генерации макета сайта.
- Если skill недоступен, продолжай работу по этим документам и не останавливай проект.

## 7. Технологический стек

Использовать:

- React;
- Vite;
- TypeScript;
- CSS Modules;
- семантический HTML;
- CSS custom properties для дизайн-токенов;
- локально подключённые шрифты в WOFF2, если лицензия разрешает распространение.

Не использовать без необходимости:

- UI-фреймворки и готовые библиотеки компонентов;
- Tailwind CSS;
- CSS-in-JS;
- тяжёлые анимационные библиотеки;
- слайдеры и карусели, которые можно реализовать простым доступным интерфейсом;
- backend, базу данных, CMS, авторизацию, платежи и внешние API.

Проект должен оставаться независимым от других лендингов портфолио. Не копируй компоненты, стили или визуальные шаблоны из стоматологии и барбершопа.

## 8. Архитектура

Организуй код по назначению. Рекомендуемое направление:

```text
src/
  app/
  components/
  sections/
  features/
    service-filter/
    visit-builder/
    booking-form/
  data/
  hooks/
  types/
  styles/
  assets/
```

Не создавай абстракции ради абстракций. Повторяющийся элемент выноси в компонент, если это улучшает читаемость или единообразие. Секции страницы должны оставаться понятными по названию.

Данные услуг, специалистов, FAQ, галереи, комплексов и временных слотов вынеси из JSX в типизированные структуры.

Основные модели:

- `ServiceCategory`;
- `Service`;
- `Specialist`;
- `GalleryItem`;
- `PackageOffer`;
- `FAQItem`;
- `TimeSlot`;
- `VisitSelection`;
- `LeadFormData`;
- `DemoFormState`.

Не использовать `any`, необоснованные type assertion и дублирование источников данных.

## 9. Главные взаимодействия

### Фильтр услуг

Категории: волосы, ногти, брови и макияж, уход.

Фильтр должен:

- работать без перезагрузки страницы;
- показывать количество услуг;
- быть доступным с клавиатуры;
- иметь понятное активное состояние;
- не скрывать выбранную услугу без предупреждения;
- корректно работать на мобильном без горизонтальной ловушки.

### Панель «Ваш визит»

После выбора услуги появляется или обновляется закреплённая панель:

- название услуги;
- продолжительность;
- цена или диапазон;
- выбранный специалист, если он задан;
- кнопка продолжения записи;
- действие «Изменить» или «Сбросить».

На desktop панель может быть встроена в правую часть интерфейса или закрепляться в пределах секции. На mobile используется компактная нижняя панель, которая не закрывает контент и учитывает safe area.

### Демонстрационная запись

Последовательность:

1. услуга;
2. специалист;
3. дата и время;
4. имя и телефон;
5. подтверждение выбранного визита;
6. демонстрационный экран успеха.

При изменении услуги должны обновляться продолжительность, цена и список подходящих специалистов. Нельзя показывать недоступного специалиста как выбранного.

Форма не отправляет сетевые запросы и ничего не сохраняет в `localStorage`, `sessionStorage`, cookies или URL. После успешного демосценария пользователь может сбросить состояние и начать заново.

## 10. Правила контента

- Все тексты — на русском языке.
- Не использовать Lorem ipsum.
- Использовать данные из `STRUCTURE.md`.
- Все вымышленные профили и предложения отмечать как демонстрационные там, где их можно принять за реальные.
- Не придумывать награды, медицинские свойства, сертификаты, рейтинги и отзывы клиентов.
- Не использовать фиктивные показатели вроде «10 000 довольных гостей».
- Цены обозначать как демонстрационные и ориентировочные.
- Не указывать реальный адрес, телефон или социальную сеть без данных пользователя.
- Карта должна быть нейтральной заглушкой, а не фальшивой интерактивной картой.

## 11. Изображения и происхождение файлов

Для каждого изображения зафиксируй:

- источник и лицензию либо точный промпт генерации;
- назначение изображения;
- корректный `alt`;
- требуемое кадрирование;
- авторство или пометку о демонстрационном происхождении.

Фотографии должны соответствовать `DESIGN.md`. Не использовать случайный набор изображений из разных салонов, эпох и цветокоррекций.

Технические требования:

- AVIF или WebP с разумным fallback при необходимости;
- `srcset` и `sizes` для крупных фотографий;
- заданные `width` и `height` или `aspect-ratio`;
- lazy loading ниже первого экрана;
- первый значимый кадр не загружать лениво;
- не растягивать небольшие изображения;
- не использовать фотографии с чужими логотипами и читаемыми брендами.

## 12. Типографика и сетка

Типографические правила из `DESIGN.md` обязательны.

- Весь интерфейс строится по 12-колоночной сетке desktop и предсказуемой мобильной сетке.
- Связанные элементы выравниваются по одним направляющим.
- Не использовать случайное абсолютное позиционирование текста.
- Не вставлять ручные `<br>` только ради совпадения с одним экраном.
- Ограничивать длину строк.
- Проверять висячие предлоги, неудачные переносы и одиночные слова.
- Цены и время выравнивать, применять tabular numerals.
- Не смешивать более двух основных гарнитур.
- Не делать основной текст мельче 16 px на мобильном.
- Капс использовать только в коротких служебных подписях.
- Не подменять иерархию одним размером и разным цветом.

## 13. Адаптивность

Обязательные контрольные ширины:

- 390 px;
- 768 px;
- 1024 px;
- 1440 px.

Дополнительно проверить промежуточные ширины, на которых меняются колонки или переносы.

На мобильном:

- нет горизонтальной прокрутки;
- текст не обрезается;
- кнопки не выходят за экран;
- изображения имеют осмысленное кадрирование;
- фиксированная панель записи не закрывает форму, FAQ и footer;
- элементы управления имеют область нажатия не менее 44 × 44 px;
- табы услуг не требуют точного свайпа для доступа к скрытому пункту.

## 14. Доступность

Целевой уровень — WCAG 2.2 AA в разумных пределах демонстрационного проекта.

Обязательно:

- семантические landmarks;
- один `h1` и последовательная иерархия заголовков;
- видимый `:focus-visible`;
- корректные `label` и сообщения об ошибках;
- управление фильтрами, FAQ, галереей и записью с клавиатуры;
- отсутствие зависимости только от цвета;
- достаточный контраст текста и интерактивных состояний;
- `aria-live` для изменения итогов записи и результата формы;
- закрытие модального интерфейса клавишей Escape, если модальный интерфейс используется;
- возврат фокуса после закрытия;
- поддержка `prefers-reduced-motion`;
- контент видим по умолчанию и не зависит от завершения анимации.

## 15. Анимация

Движение должно напоминать спокойный сервисный ритуал, а не рекламное шоу.

Допустимо:

- мягкое появление фотографий через маску без скрытия контента;
- короткий сдвиг индикатора категории;
- плавное обновление панели «Ваш визит»;
- аккуратное раскрытие FAQ;
- один согласованный переход между шагами записи.

Запрещено:

- параллакс на каждом блоке;
- постоянное движение декоративных элементов;
- курсор-эффекты;
- тяжёлый WebGL;
- пружинящие кнопки;
- анимации, мешающие быстро прочитать цены.

## 16. Производительность и SEO

Цели Lighthouse:

- Performance ≥ 90;
- Accessibility ≥ 95;
- Best Practices ≥ 90;
- SEO ≥ 90.

Минимальные требования:

- корректные `title` и `meta description`;
- Open Graph данные для демонстрационного проекта;
- понятный `lang="ru"`;
- favicon и theme-color;
- отсутствие блокирующих тяжёлых зависимостей;
- оптимизированные изображения и шрифты;
- минимизация layout shift;
- понятные ссылки и кнопки;
- контент страницы доступен без JavaScript-анимаций.

Не добавлять фиктивную разметку `LocalBusiness`, реальные координаты, рейтинг или отзывы в JSON-LD. При необходимости использовать только честную разметку, соответствующую концептуальному проекту.

## 17. GitHub Pages

Подготовь проект к отдельной публикации на GitHub Pages:

- настрой `base` в Vite под имя репозитория;
- используй относительные пути через импорт или `BASE_URL`;
- избегай маршрутизации, которая ломается при прямом обновлении страницы;
- добавь GitHub Actions workflow для typecheck, build и публикации;
- не выполняй реальный deploy без явного разрешения пользователя.

## 18. Проверка

Перед завершением работы:

1. Выполни TypeScript typecheck.
2. Выполни production build.
3. Проверь страницу на 390, 768, 1024 и 1440 px.
4. Сделай полностраничные desktop- и mobile-снимки.
5. Визуально проверь сетку, ритм, переносы, изображения и состояния элементов.
6. Проверь фильтры и сохранение выбранной услуги.
7. Пройди все шаги записи.
8. Проверь пустые, ошибочные, слишком длинные и корректные значения.
9. Проверь успешный экран и полный сброс.
10. Пройди страницу только клавиатурой.
11. Проверь `prefers-reduced-motion`.
12. Проверь отсутствие сетевых запросов формы и сохранения данных.
13. Запусти механическую проверку `impeccable`, если skill доступен.
14. Исправь найденные материальные проблемы и повтори один итоговый визуальный проход.

## 19. Критерии готовности

Проект готов, когда:

- реализованы все обязательные секции из `STRUCTURE.md`;
- дизайн соответствует `DESIGN.md` и не похож на первые два сайта;
- премиальность выражена композицией и деталями, а не клише;
- услуги, цены и путь к записи понятны без объяснений;
- выбранная услуга сохраняется в сценарии записи;
- форма полностью работает как демосценарий;
- сайт адаптивен и доступен с клавиатуры;
- изображения оптимизированы и имеют происхождение;
- typecheck и production build проходят без ошибок;
- явно указано, что сайт концептуальный, а заявки не отправляются;
- проект технически готов к GitHub Pages, но не опубликован без разрешения.
